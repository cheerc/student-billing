## 2. Findings

### N01 — P2 — 真實 ERP 檔的 OOXML 形狀無法被合成 fixture 覆蓋

**plan 位置**：`07:20`（ExcelJS 閘門「先通過真實ERP與欄位重排／隱藏fixture」）、`07:77`（T01「ExcelJS轉為中立raw row；rich text等儲存型態須有明確可測的文字化規則」）。
**spec 依據**：`02:40`（「Excel 原生 sharedStrings／inlineStr 都須讀得出」）、`04:22`（「真實樣本留本機，未來Git／CI使用合成或一致匿名化fixture」）、`04:78`（I02）、`04:81`（I05）。

**原始證據**（直讀 `xl/worksheets/sheet1.xml`）：

|特徵|ERP 學生檔|計算檔 Sheet1|
|---|---|---|
|`sharedStrings.xml`|**不存在**|存在|
|字串儲存型態|**inlineStr ×3,652（100%）**|sharedString|
|`<dimension>`|**無**|有|
|產生器痕跡|`<row  r="1">`、`<cols >`（雙空白，非 Excel 原生寫法）|Excel 原生|
|隱藏列／欄|目前 0；`autoFilter` 存在|—|

**觸發例**：I02（欄位重排）與 I05（隱藏列欄）的 fixture 若以 ExcelJS／openpyxl 產生，輸出必然含 `sharedStrings.xml` 與 `<dimension>`。這些測試會綠燈，但走的是**與正式輸入不同的解析分支**。若 ExcelJS 在 inlineStr 或缺 dimension 時有邊界行為（例如 `actualRowCount` 推導、`cell.value` 對 `<is><t xml:space="preserve">` 的處理），只有「上傳真實檔」那一條路徑會踩到。

**影響**：`04:22` 明訂未來 CI 不放真實樣本，屆時 CI **完全沒有 inlineStr 覆蓋**。這不是現在會錯算，而是回歸保護有洞——正式輸入的形狀恰好是唯一沒被合成 fixture 覆蓋的那一種。

**最小修正**：在 `04` 的 fixture 管理加一句、並於 T01 落實——**匿名化 fixture 必須保留來源的 OOXML 儲存形狀**（inlineStr、無 dimension、無 sharedStrings），做法是「複製原檔 → 就地替換 `<t>` 文字 → 不經函式庫重寫」，而非用函式庫重新產生。另在 T01 的 adapter 契約測試明列三個斷言：inlineStr 可讀、缺 `<dimension>` 時筆數仍為 477、`xml:space="preserve"` 的前後空白依 `02:38` 規則處理。

**應在**：T01。
**驗收**：`npm run test:integration` 在**不含真實樣本**的情況下，仍有一個 inlineStr/無 dimension 的 fixture 通過 I01/I05。

### N02 — P2 — 初始 alias 對照的真實規模未進 fixture，含 3 組純命名漂移

**plan 位置**：`07:90`（T02 班級候選）、`07:131`（T05「一般輔導A/B為2待設定＋舊班1本批未出現，明確顯示此為該科別範圍」）、`07:162`（5.1 alias 候選預覽）。
**spec 依據**：`01:79`（雙向對照三態）、`04:110`（I19）、`02:57`（正式名單依 classId、legacy 抽取鍵只管天數）。

**原始證據**：以 plan `07:162` 規定的規則（剝 yearPrefix、取至 `[團]` 的 baseName、完整相等且無歧義才提候選）對全量實算：

|類別|數量|
|---|---:|
|ERP 不同 token|95|
|收斂後 ERP baseName|54|
|**與 seed 唯一精確相符（可自動提候選）**|**42**|
|**seed 無對應（進待設定）**|**12**|
|baseName 歧義（一對多）|**0**|
|seed 有、ERP 本批無對應|7|

12 個待設定 baseName（括號為報名筆數）：`交通車`(103)、`小六國文加強班`(35)、`小六數學加強班`(26)、`正音A班`(24)、`正音B班`(21)、`國小輔導-寫功課`(19)、`國小輔導-四年級A`(17)、`兒童美語` 以外的 `小六英文加強班`(18)、`國小數學-一`(13)、`國小輔導-四年級B`(12)、`國小國語文-小三四`(12)、`美語等班`(2)。

其中 **3 組是純命名漂移，自動候選規則永遠配不上，但明顯是同一批課**：

```
ERP 115國小國語文-小三四[團]      ↔  seed 國小國語文-小三小四[團]     （少一個「小」）
ERP 115小六國文加強班[團][小六]    ↔  seed 小六加強班-國文[團]        （詞序不同）
ERP 115小六數學加強班[團][小六]    ↔  seed 小六加強班-數學[團]        （詞序不同）
另：seed 有 小六加強班-自然，ERP 有 115小六英文加強班 —— 兩邊各有一科無對應
```

**觸發例**：使用者第一次進課程設定頁，會同時看到 12 個待設定 ERP baseName 與 7 個本批未出現的 seed 班。要把 `小六國文加強班` 對上 `小六加強班-國文`，只能靠人工在兩份清單間目視配對；plan 沒有規定要把「未對應的 seed 班」並列在同一畫面供挑選。

**影響**：不影響計算（這些科別都不參與 `國小數學-`／`兒童美語-` 抽取，也不改科數），但影響展示 A/B 的可判讀性與 T05 的可操作性。另外 `07:131` 的「2待設定＋1本批未出現」是**一般輔導子集**的數字（plan 已誠實標註範圍），驗收時容易被誤讀成全機構總量。

**最小修正**
1. `verify:fixtures` 增加初始對照總量斷言：**42 自動候選 / 12 待設定 / 7 seed 未出現 / 0 歧義**，與現有「一般輔導 2＋1」並列並標明各自範圍。
2. T05 設定頁的待設定清單**同畫面並列「本批未出現的 seed 班」**，讓人工配對不必跨頁；仍維持 `07:162` 的「不自動批准」。
3. `國小輔導-寫功課` 進待設定屬預期（seed 無此班），請在 fixture 註明，避免被當成漏建。

**應在**：T02（總量數字）、T05（並列 UI）。
**驗收**：`npm run verify:fixtures` 輸出上述四個數字；T05 畫面可在不離開頁面的情況下完成一組命名漂移的映射。

### N03 — P2 — `activate` 未明寫 `expectedRevision`，與 `03:89` 的字面要求有落差

**plan 位置**：`07:118`（T04「接入ready→calculate→completed→activate……切換active採原子交易」）、`07:5.2`（「提交交易內重新比對active revision與所有input hash；insert完整結果後CAS更新active_state」）。
**spec 依據**：`03:89`（`POST /imports/{previewId}/activate`｜**body 帶 expectedRevision**；可用 idempotencyKey 防止連按）。

**證據**：plan 對 `POST /settings/preview` 明寫 expectedRevision（`07:133`），對 activate 只寫 idempotencyKey（`07:5.2`），未出現 expectedRevision 字樣。機制上 `07:5.2` 的「交易內重新比對 active revision」已涵蓋，但那是通則描述，不是該 endpoint 的契約。

**觸發例**：兩個分頁各自開著不同 previewId，先後按「使用這批資料」。idempotencyKey 不同（不同 body），兩次都會通過；第二次覆蓋第一次的 active，使用者不會收到 409，只會看到 active 無聲換掉。

**影響**：屬 lost-update 類的一致性缺口，但只影響「誰的批次成為 active」，不造成錯算或資料損毀，且單機無登入情境下發生機率低。

**最小修正**：T04 的 activate 契約明列 `expectedRevision`（值取自 `GET /runs/current` 的 ActiveState revision），版本不符回 409，與 `03:132` 的錯誤碼一致；`07 §7` 的 T03–T04 完成定義加上「activate 409」一條。

**應在**：T04。
**驗收**：整合測試「兩個 preview 以相同 expectedRevision 先後 activate，第二次回 409 且 active 不變」。

### N04 — P2 — U47 的固定 fixture 人數未載明，且正是最容易被「修成全綠」的一組

**plan 位置**：`07:110`（T03 第 4 組含 U43–47）、`07:124`（展示 B 驗收「篩出5筆級距差異及13人排課缺漏」）、`07:239`（「不為得到全綠而修改原資料」）。
**spec 依據**：`04:81`（U47「缺排課但計算fallback等於ERP級距｜tierComparison=match且計算needs_review；不能因match消除警告」）。

**原始證據**：我以標籤為來源、不套別名重算後交叉比對——13 名 `schedule_not_found` 學生**全部 13 人**的 `tierComparison` 都是 `match`：

```
列 11  小一 115國小輔導-一A[團]        ERP 5     算出 5     match
列 222 小一 115國小輔導-一B[團][4]     ERP 4     算出 4     match
列 258 小一 115國小輔導-一A[團][4]     ERP 4     算出 4     match
列 264 小一 115國小輔導-一A[團][4_5]   ERP 4.5   算出 4.5   match
…（共 13 筆，無一例外）
```

**觸發例**：實作者若把 U47 理解成「邊界案例，樣本可能 0～1 筆」，很可能用合成 fixture 敷衍。實際上這是樣本中一個**滿載**的組合狀態：13 人同時 `match` + `needs_review`。而 `07:124` 的展示 B 驗收只說「篩出 5 筆級距差異及 13 人排課缺漏」，若 UI 把 `match` 當成「沒問題」而不顯示警告，這 13 人會從兩個篩選條件中同時消失（級距沒差異、警告被 match 吃掉），驗收反而看起來通過。

**影響**：這正是 r2 F04／`01:59`「match 但缺排課也須保留警告」要防的情形，且樣本規模最大化，值得寫成固定數字而非口頭要求。

**最小修正**：`04` 的 U47 與 `07:124` 補上「固定 fixture：13 人 tierComparison=match 且 scheduleStatus=schedule_not_found，兩個狀態同時存在」；展示 B 驗收改為「以 tierMismatch=false 篩選時，這 13 人仍出現在 hasIssues 清單」。

**應在**：T03（規則層）、T04（驗收條文）。
**驗收**：I17 增一條斷言：`tierMismatch=false AND hasIssues=true` 的結果集恰含這 13 人。

### N06 — P3 —（可選）compat 逐人結果可改為即時計算，省一份與正式結果等大的儲存

**plan 位置**：`07:121`（「診斷比較**可**在建立run時一起保存，GET只讀」）、`07:5.4`（A/B/C 三步診斷）。
**spec 依據**：`03:110`（comparison「為P1唯讀診斷，固定同輸入」）。

**說明**：我原本懷疑雙軌是過度設計，回查後確認 **`03:110` 明文把 comparison 列為 P1**，plan 是忠實落實，**不是範圍膨脹**。此處只提一個可選的最小化：

comparison 的輸入（import 快照、設定快照、規則版本）在 run 內全部固定，因此 compat 結果是輸入的純函式，**即時計算與預先儲存結果完全相同**。477 人規模下即時計算約與一次重算同級（plan 自訂目標 1 秒內），對一個診斷頁可接受，而預存會讓 `results`／`enrollment_results` 各多一份等大資料。`07:121` 用的是「可」，已經保留彈性；建議把預設定為**即時計算、不落庫**，等 bench 顯示診斷頁慢到影響操作再改預存。

若採預存，請在 `07:5.2` 的物理表說明裡明確標示 compat 列的區分欄位與清理策略，避免 `results` 被誤讀成正式結果的兩倍筆數。

**應在**：T04（擇一即可，兩者都正確）。

## 4. 切片與範圍評估

**展示 A（T00–T02）可獨立交付，且沒有被不必要的工作拖住。** 我特別檢查了「第一個展示前是否塞太多基礎工作」：T00 只建 migration 骨架與空頁面，`07:68` 明寫「其餘表在需要的切片加入，不先做完整雲端資料抽象」；T01 的 token 解析是名單顯示本身需要的；T02 的班級候選來自 **ERP token 的結構化 identity**，不依賴 seed 與計算——我已驗證 45 個 seed 班名與 ERP token **無一字面相等**，所以展示 A 必須走 ERP identity 這條路，plan 的選擇是唯一可行且最短的。
